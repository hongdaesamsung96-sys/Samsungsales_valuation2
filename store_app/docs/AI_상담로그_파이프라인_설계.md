# AI 기반 상담 반응 로그 자동화 - 설계안

상담원이 매번 앱에 직접 입력하는 대신, 상담 대화를 녹음 → 텍스트 변환 → AI 분석을 거쳐
`sales_talk_log`(wow포인트/구매결정포인트/고객반응/전환여부)를 자동으로 채우는 파이프라인 설계다.
이 문서는 설계와 법적 고려사항까지만 다루며, 실제 STT/LLM API 키 발급과 연동은 회사 인프라팀에서
진행해야 한다(이 세션은 외부 API 호출용 네트워크가 막혀 있어 직접 구현·테스트는 불가능).

## 1. 전체 흐름

```
[상담 현장 녹음]
     │  (태블릿/전용 녹음기, 상담원이 대화 당사자로서 녹음)
     ▼
[STT: 음성→텍스트 변환]
     │  Naver Clova Speech / Google STT / Whisper 중 택1
     ▼
[LLM 분석: 구조화 추출]
     │  Claude API 등에 상담 스크립트 원문 + 추출 스키마를 프롬프트로 전달
     ▼
[구조화된 로그 생성]
     │  wow_point, decision_point, customer_reaction, purchase_converted,
     │  age_group/gender(통계용, 개인 식별 아님), segment_id 추정, 사용된 script_id 매칭
     ▼
[sales_talk_log 테이블 저장]  (source = "ai_transcribed")
     │
     ▼
[매장 태블릿 앱에 자동 반영]  (기존 동기화 API 그대로 재사용)
```

이미 만들어둔 DB 스키마의 `sales_talk_log.source` 컬럼이 `manual`/`ai_transcribed`를 구분하도록 설계돼
있어, 이 파이프라인은 기존 구조를 그대로 활용하면 된다. `server/sync_server.py`의
`POST /api/sales_talk_log`도 그대로 재사용 가능(호출 주체가 사람이든 AI 파이프라인이든 동일 API).

## 2. 단계별 기술 옵션

**STT (음성→텍스트)**: 한국어 상담 특화라면 네이버 클로바 스피치(Clova Speech)가 사투리/전문용어
인식률이 무난하고, 글로벌 옵션으로는 Google Cloud Speech-to-Text, OpenAI Whisper(자체 호스팅 가능)가 있음.
매장 소음 환경을 고려해 잡음 제거 전처리가 필요할 수 있음.

**LLM 분석**: STT 결과 텍스트를 Claude API에 전달해 아래와 같은 구조화 스키마로 추출.

```json
{
  "customer_reaction": "긍정 | 중립 | 부정",
  "wow_point": "고객이 특히 반응한 지점 (1문장 요약)",
  "decision_point": "구매 결정에 영향을 준 요인 (1문장 요약)",
  "purchase_converted": "Y | N | 불확실",
  "residence_area_hint": "인근 거주 | 인근 직장 | 타 지역 | 미상 (참고용 - 최종 확정은 상담원 버튼 태깅)",
  "mentioned_products": ["언급된 제품/모델명"],
  "estimated_segment": "SEG_UPGRADE | SEG_FAMILY | SEG_YOUNG | SEG_VIP | SEG_STUDENT",
  "matched_script_id": "SC001 등, 유사도가 가장 높은 스크립트"
}
```

이 스키마에는 이름·연락처·고객ID 등 개인 식별값을 의도적으로 포함하지 않는다(3-2절 참고). `age_group`,
`gender`, `residence_area`(인근 거주/인근 직장/타 지역/미상 - 구체 주소 아님)는 AI가 음성에서 자동
추정하지 않고 상담원이 앱에서 버튼으로 직접 태깅하는 값을 그대로 사용할 것을 권장한다(이유는 3-3절 참고).

**매장을 미리 유형으로 분류하지 않는다는 원칙**: 초기 설계에서는 매장마다 "오피스형/주거형/학원가형"
같은 유형을 미리 붙이고 그 유형에 맞는 고객층을 가정했었다. 하지만 실제로 필요한 것은 정반대다 —
매장은 매장명/위치로만 구분하고, 그 매장에 어떤 연령대·성별·거주형태 고객이 많이 오는지는 `sales_talk_log`가
쌓인 뒤 실측 집계로 알아낸다. 그래야 선입견 없이 매장별로 실제 다른 고객유형 패턴을 발견할 수 있다
(예: "이 매장은 원래 오피스 상권이라 30대가 많을 것"이라는 가정이 아니라, "상담로그를 보니 실제로 20대가
많고 인근 직장인 비중이 높다"는 식으로 데이터가 먼저 말해주는 구조).

프롬프트 설계 시 "추측하지 말고 확실하지 않으면 불확실로 표기" 같은 지침을 넣어 과신 추출을 방지해야 함
(전환여부처럼 매출과 직결되는 값은 오분류 시 통계가 왜곡되므로 보수적으로 설계).

## 3. 법적/윤리적 고려사항 (중요)

이 부분은 실제 도입 전 사내 법무팀 검토가 필요하며, 아래는 일반적인 원칙 정리이지 법률 자문이 아니다.

### 3-1. 녹음의 적법성

한국 통신비밀보호법상, 대화 당사자(상담원 본인)가 자신이 참여한 대화를 녹음하는 것은 상대방(고객) 동의
없이도 위법이 아니다. 다만 녹음 사실을 고객에게 사전 고지하는 것이 원칙으로 권장된다(매장 입구/상담
데스크 안내문, 상담 시작 시 구두 고지 등).

### 3-2. "실시간 변환이라 녹음본을 안 남기면 괜찮다"는 오해

원음을 저장하지 않고 실시간으로 텍스트만 만들어도 개인정보보호법상 의무가 사라지는 것은 아니다. 개인정보
보호법이 규율하는 "처리"에는 수집·생성·기록·이용이 모두 포함되므로, 실시간 변환 자체가 이미 처리 행위에
해당한다. 관건은 저장 형식(음성/텍스트)이 아니라 **그 결과물이 특정 개인을 식별할 수 있는지**다.

- 결과물이 customer_id·이름·연락처 등과 연결돼 특정 고객을 알아볼 수 있다면, 원음을 안 남겨도 여전히
  개인정보 처리로 취급돼 목적 고지·동의 의무가 남는다(특히 마케팅 활용 목적은 별도 고지 필요).
- 반대로 결과물이 특정 개인과 연결되지 않고 store_id + 연령대/성별 + 세그먼트 같은 집계 단위로만
  남는다면, 개인정보보호법 제28조의2(가명정보의 처리)에 따라 통계작성 목적으로는 별도 동의 없이 처리할
  수 있다.

이 프로젝트는 판촉 타겟 세그먼트 분석, 유효 세일즈톡 검증, 상권별 고객유형 차이 파악이 목적이지 특정
개인 추적이 목적이 아니므로, `sales_talk_log`를 **후자(비식별 집계) 방식으로 설계**했다. 이번 개편에서
`customer_id` 컬럼을 완전히 제거하고 `age_group`/`gender`만 남긴 이유가 이것이다.

### 3-3. 연령대/성별을 "AI 음성 추정"이 아닌 "상담원 수기 태깅"으로 하는 이유

음성에서 AI가 자동으로 나이·성별을 추정하는 것은 그 자체로 생체정보 기반 추론에 해당해 별도의 민감정보
이슈를 만들 수 있고, 추정 오류로 통계가 왜곡될 위험도 있다. 반면 상담원이 대화 중 육안·문답으로 판단해
앱의 버튼(연령대 5종, 성별 3종)을 한 번 누르는 방식은 다음 이유로 더 낫다.

- 입력값이 애초에 카테고리 수준(예: "30대", "여성")이라 개인 식별로 이어질 위험이 낮다.
- 생체정보 추론 절차가 없어 추가 규제 이슈가 생기지 않는다.
- 상담 흐름을 끊지 않고 1~2초 안에 태깅 가능해 실무 적용성이 좋다.

다만 아주 작은 매장에서 특정 시간대에 방문객이 1명뿐인 경우처럼, 연령대+성별+매장+날짜 조합만으로도
"그날 그 시간 그 고객"이 정황상 특정될 가능성은 이론적으로 남는다. 이를 위해 데이터 분석 내역에 대한
접근 권한을 본사·지사 관리자로 제한했다 (3-6절 참고).

### 3-4. 데이터 최소화·보관정책

음성 원본은 STT 변환 후 즉시 폐기하고 저장하지 않는다. 저장되는 것은 store_id, staff_id, 연령대/성별,
세그먼트, 사용 스크립트, 반응, wow포인트, 결정포인트, 전환여부뿐이며 개인 식별값은 애초에 수집하지 않는다.

### 3-5. 상담원 관련 이슈

상담원의 발화도 함께 녹음·분석되므로, 이를 상담원 평가/감시 목적으로 오용하지 않는다는 내부 방침과
상담원 대상 고지도 별도로 필요할 수 있음(노무 이슈로 이어질 수 있어 인사팀 협의 권장).

### 3-6. 접근 권한 설계 (구현 완료)

"데이터 분석 내역은 본사·지사 관리자만 확인 가능"이라는 정책을 화면상 안내에 그치지 않고 서버에서
강제하도록 구현했다 (`server/sync_server.py`). 역할은 3종이다.

| 역할 | 범위 | 볼 수 있는 것 | 볼 수 없는 것 |
|---|---|---|---|
| `staff` (상담사) | 자기 매장 1곳 | 세일즈톡 참고자료(세그먼트/스크립트), 본인이 입력한 로그(이번 세션 한정) | 상권분석, 통계, 타 상담사/타 매장 로그, CRM 고객 목록 |
| `branch_manager` (지사 관리자) | 소속 지사 산하 매장 전체 | 상권분석, 세그먼트 분포, 세일즈톡 로그 열람, 통계 (지사 범위) | 다른 지사 데이터 |
| `hq_manager` (본사 관리자) | 전국 전체 | 위 전체 + 지사별 비교(전사 관점) | - |

로그인 시 서버가 역할(role)과 범위(store_id 또는 branch_id)를 담은 서명 토큰을 발급하고, 이후 모든
API 요청은 이 토큰을 검사해 범위를 벗어난 매장 데이터는 아예 반환하지 않는다(클라이언트 화면을 조작해도
서버가 걸러낸다). 예를 들어 상담사 토큰으로 `/api/manager/export`를 호출하면 403이 반환되고, 지사
관리자가 다른 지사 매장에 로그를 기록하려 하면 403이 반환된다 — 프로토타입에서 실제로 확인함.

이 프로토타입의 인증은 표준 라이브러리(hmac)로 직접 구현한 서명 토큰이며, 데모 계정(`staff_gangnam`,
`branch_sudokwon`, `hq_admin` 등, 비밀번호 `pass1234`)도 코드에 하드코딩돼 있다. 실제 운영 전환 시
반드시 다음으로 교체해야 한다.

- 평문 비밀번호 하드코딩 → 사내 SSO/사번 인증 연동 (LDAP, OAuth2 등)
- 고정 `SECRET_KEY` → 환경변수/시크릿매니저로 분리, 주기적 로테이션
- HTTP → 반드시 HTTPS 위에서만 토큰 송수신

## 4. 단계적 도입 로드맵 제안

1. **파일럿**: 1~2개 매장에서 상담원 동의 하에 시범 운영, 고지문/동의서 초안 마련
2. **법무 검토**: 고지문, 개인정보처리방침 반영, 보관기간 정책 확정
3. **정확도 검증**: AI 추출 결과 vs 상담원 수동 입력 결과 비교, 추출 정확도 기준치 설정
4. **전사 확대**: 검증 완료 후 전국 매장 순차 적용, `source=ai_transcribed` 데이터 비중 모니터링
